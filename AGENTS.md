==================================================
## ОБЩИЕ ПРАВИЛА РАБОТЫ
==================================================
- Отвечай на русском.
- Будь кратким.
- Не переписывай проект целиком.
- Делай минимальные точечные изменения.
- Одна задача — минимальный набор правок.
- Не ломай текущие контракты и существующий функционал.
- Если меняешь сигнатуру — обнови все вызовы в рамках этой же задачи.
- Всегда сначала анализируй текущую реализацию, потом предлагай патч.
- Перед любыми правками покажи:
  1) краткий разбор причины
  2) какие файлы меняешь
  3) почему это минимальный патч
- После правок всегда показывай diff.
- Не делать полную перезапись файла скриптом, если задача решается точечным patch.
- Если файл большой, меняй только нужные участки.
- Удаляй мёртвый код, только если он явно относится к текущей задаче.
- Не использовать push --force и не предлагать переписывать историю git.
- Все имена новых файлов и артефактов — латиницей.
- Если создаешь архивы/файлы для скачивания — имя ссылки и файла только латиницей.

==================================================
## ПРАВИЛА ПРОЕКТА
==================================================

Перед стартом любой задачи в ответе указывай:
- TASK-GUIDE
- Старт по Москве строкой

Пример:
TASK-GUIDE
Старт по Москве: 09.04.2026 10:15 MSK

Дополнительные правила:
- Файлы >300 строк: внимательно проверяй импорты, скобки, типы.
- Над измененной функцией добавляй комментарий: что и почему изменено с пометкой в начале GPT
- Для UI-строк:
  - не делать опасные replace кириллицы через powershell
  - если в файле уже есть проблемы mojibake, новые/изменяемые русские UI-строки писать через \uXXXX
- Все новые UI-строки выносить в централизованный словарь, а не писать inline, если задача это затрагивает.
- Использовать UTF-8 without BOM.
- Пользователь базового уровня в программировании: поясняй названия файлов и шаги простыми словами.


==================================================
## ПРАВИЛА ДЛЯ КОДА
==================================================

Перед добавлением новых вызовов:
- убедись, что импорт существует
- если нужен новый импорт — добавь его

Для любых исправлений:
- сначала найди точку причины
- потом внеси минимальную правку
- потом проверь сборку

Если задача касается backend/API:
- проверь соответствие frontend endpoint и backend route
- проверь payload и response contract
- проверь, не ломаются ли cookie/auth headers

==================================================
## ЕСЛИ НУЖНО ВНЕСТИ ПРАВКИ
==================================================

Всегда придерживайся стратегии:
- сначала минимальный патч
- потом проверка
- потом следующий шаг

Никогда не делай сразу огромную серию переписываний.

==================================================
## ЧТО ДЕЛАТЬ ПРИ БАГЕ
==================================================

Если пользователь описывает баг:
- сначала локализуй корень проблемы
- не предлагай переписать всё
- покажи точечный diff
- объясни, почему это минимальный патч
- после правки обязательно проверь сборку

==================================================
## ГЛАВНОЕ ПРАВИЛО
==================================================

Сохраняй уже внесенные изменения и продолжай работу поверх них.
Твоя задача — аккуратно развивать проект, а не переделывать его заново.
- Before patching behavior: reproduce the exact user flow in UI and verify that functionality is truly missing (not only misconfigured).

AGENTS EXTENSIONS (MERGED RULES)

0. Неприкосновенные правила
- Без лести и воды.
- Не соглашаться с неверными предпосылками.
- Не выдумывать (пути, API, результаты).
- При неясности — спрашивать.
- Менять только необходимое.

1. Перед кодом
- Короткий план (1–2 предложения) или шаги с проверками.
- Прочитать изменяемые файлы и их вызовы.
- Следовать паттернам проекта.
- Явно проговорить предположения.
- При наличии альтернатив — показать варианты и трейд-оффы.

2. Простота
- Минимальный код под задачу.
- Без “на будущее”.
- Обрабатывать только реальные ошибки.
- Упростить, если можно.

3. Точечные изменения
- Не трогать лишнее.
- Без “заодно рефакторинга”.
- Удалять только свой мусор.
- Соблюдать стиль проекта.

4. Работа от цели
- Формулировать проверяемый результат.
- Писать проверку (тест/скрипт).
- Запускать и проверять.
- Чинить причину, не тест.

5. Инструменты
- Запускать код, а не гадать.
- Не считать задачу завершенной без проверки.
- Читать логи полностью.
- UI — проверять визуально.

6. Гигиена
- После 2 неудач — остановка.
- Использовать подагентов для анализа.
- Нормальные commit-сообщения.

7. Коммуникация
- Коротко и прямо.
- Без лишней структуры.
- Только по делу.

8. Когда спрашивать
- Если неоднозначность влияет на результат.
- Если затрагивается критичный код.
- Если нужен доступ/секрет.
- Если есть конфликт целей.

9. Самоулучшение (в рамках текущего файла)
- Добавлять правила только если они предотвращают реальные ошибки.
- Удалять лишние правила.
