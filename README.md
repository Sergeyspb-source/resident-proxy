# exitnode

Выход в интернет через компьютеры коллег. Клиент подключается к SOCKS5 на VPS1,
трафик идёт по цепочке VPS1 → VPS2 → ПК коллеги → сайт. Сайт видит домашний IP
коллеги, а не IP клиента и не IP серверов.

```
браузер
  │ SOCKS5 (только внутри VPN)
  ▼
VPS1   WireGuard + проброс порта       (кода нет)
  ▼
VPS2   relay: SOCKS5 + приём агентов   (этот бинарник)
  ▼ mTLS + yamux, агент сам звонит наружу
ПК коллеги   agent: туннель + панель + фильтры
  ▼
сайт
```

## Что видит кто

| Сторона | Видит | Не видит |
|---|---|---|
| Сайт | IP коллеги | клиента, VPS1, VPS2 |
| Коллега | IP VPS2 | IP клиента, VPS1 |
| VPS2 | IP коллеги и VPS1, хеш ключа, фиктивный адрес | IP клиента, сам ключ, настоящий сайт, содержимое |
| VPS1 | IP клиента и VPS2 | коллегу, содержимое HTTPS |

Волонтёру не нужен белый IP: агент сам открывает исходящее соединение к VPS2,
поэтому работает за NAT и CGNAT.

## Сборка

Windows-версия без чёрного окна консоли:

```
go build -ldflags "-H=windowsgui -s -w" -o bin/proxy.exe ./cmd/proxy
```

Логи пишутся в `agent.log` рядом с `proxy.exe`. Состояние (ключи, квоты) —
в `%LOCALAPPDATA%\exitnode\agent-state.json`, в приватном каталоге пользователя.

Нужен Go 1.26.11 — он подтянется автоматически по `toolchain` в `go.mod`.

Для Linux-шлюза:

```
GOOS=linux GOARCH=amd64 go build -ldflags "-s -w" -o bin/exitnode ./cmd/proxy
```

## Установка (Windows)

Установщик — это тот же `proxy.exe` в режиме `setup`. Он копирует программу в
`%LOCALAPPDATA%\exitnode`, создаёт ярлык на рабочем столе, запись в «Удаление
программ» и, для узла, автозапуск.

Узел выхода (у коллеги):

```
proxy.exe setup --agent --invite agent.exitnode
```

Приглашение узла скачивается в панели: «Настройки» → «Скачать agent.exitnode».
Передайте коллеге `proxy.exe` и этот файл.

Клиент:

```
proxy.exe setup --client
```

После этого файлы `.exitnode` открываются клиентом: достаточно дважды щёлкнуть
приглашение. Удаление:

```
proxy.exe setup --uninstall
```

Подписи кода нет, поэтому при первом запуске SmartScreen покажет «Неизвестный
издатель» → «Подробнее» → «Выполнить».

## VPS2 — шлюз

Нужен TLS-сертификат на домен, который указывает на VPS2 (Let's Encrypt).

```
./exitnode relay \
  -socks 10.9.0.2:1080 \
  -tunnel :2053 \
  -cert /etc/letsencrypt/live/proxy.example.com/fullchain.pem \
  -key  /etc/letsencrypt/live/proxy.example.com/privkey.pem \
  -socks-tls \
  -token-file /etc/exitnode/token
```

- `-socks 10.9.0.2:1080` — адрес в туннеле до VPS1, а не `0.0.0.0`. Так порт
  физически недоступен из интернета.
- `-tunnel :2053` — сюда подключаются агенты коллег. Порт можно любой свободный;
  2053 взят потому, что 8443 часто занят VPN, а 2053 редко блокируется провайдерами.
- `-socks-tls` — шифрует SOCKS5 тем же сертификатом. Без этого ключ клиента
  пошёл бы открытым текстом, поэтому вне `-dev` режим запрещён.
- `-token-file` — файл с общим секретом агентов (минимум 32 символа).
  Токен в командной строке виден другим пользователям VPS, файл — нет.
- `-dev` — только для локальной сети: разрешает работу без TLS и короткий токен.

systemd:

```ini
[Unit]
Description=exitnode relay
After=network.target

[Service]
ExecStart=/opt/exitnode/exitnode relay -socks 10.9.0.2:1080 -tunnel :2053 \
  -cert /etc/letsencrypt/live/proxy.example.com/fullchain.pem \
  -key /etc/letsencrypt/live/proxy.example.com/privkey.pem \
  -socks-tls -token-file /etc/exitnode/token
Restart=always
RestartSec=3
User=exitnode

[Install]
WantedBy=multi-user.target
```

## VPS1 — проброс без кода

Клиент ходит в VPN, поэтому SOCKS5 должен слушать только адрес в туннеле.

Через `socat` (проще всего):

```
socat TCP-LISTEN:1080,bind=10.8.0.1,fork,reuseaddr TCP:10.9.0.2:1080
```

Через nftables (быстрее, но нужен `ip_forward` и MASQUERADE):

```
sysctl -w net.ipv4.ip_forward=1
nft add rule ip nat prerouting ip daddr 10.8.0.1 tcp dport 1080 dnat to 10.9.0.2:1080
```

Порт 1080 на публичном интерфейсе VPS1 закрыть файрволом.

## ПК коллеги — агент

```
proxy.exe agent -relay proxy.example.com:2053 -token "длинный-случайный-токен" -name "Anna-Tallinn"
```

При запуске открывается окно-приложение (Edge или Chrome в режиме `--app`:
без адресной строки и вкладок) и иконка в трее. Закрытие окна ничего не
останавливает, полный выход — через меню иконки.

Что показывает панель:

- **Обзор** — кнопка включения, принято/отдано, скорость, график,
  таблица активных подключений и «Остановить все»;
- **Пользователи** — свой ключ, свои сайты, своя квота и скорость у каждого,
  расход за день и месяц, кто сейчас онлайн;
- **Настройки** — автозапуск, ресурсы процесса и всего компьютера.

Полезные флаги:

| Флаг | Смысл |
|---|---|
| `-ports 80,443` | какие порты разрешены (по умолчанию 80 и 443) |
| `-max-sessions 8` | лимит одновременных подключений |
| `-quota-mb 0` | квота по умолчанию для новых ключей, МБ в сутки (0 = без лимита) |
| `-quota-month-mb 0` | квота по умолчанию для новых ключей, МБ в месяц |
| `-rate-kbps 0` | скорость по умолчанию для новых ключей, КБ/с |
| `-allow-domains ""` | сайты по умолчанию для новых ключей |
| `-ui 127.0.0.1:17890` | адрес панели |
| `-tray` | не открывать окно при старте, только иконка в трее |
| `-public-socks` | адрес шлюза для приглашений, например `cdn.example.com:2084` |
| `-token-file` | файл с токеном вместо `-token` (не виден в командной строке) |
| `-server-name` | имя в сертификате, если оно отличается от адреса |
| `-insecure` | не проверять сертификат (только для теста) |

### Автозапуск

Галочка «Запускать при входе в Windows» в панели пишет запись в
`HKCU\Software\Microsoft\Windows\CurrentVersion\Run` с флагом `-tray`, то есть
после входа программа появляется только иконкой в трее. Галочка снимается там же.
Права администратора не нужны.

## Ключи доступа

Пока ключей нет, к узлу не может подключиться никто. Это сделано специально:
доступ выдаёт владелец компьютера, а не администратор шлюза.

Модель как в SSH, но проще:

1. В панели, вкладка «Пользователи», впишите подпись (например, «Иван») и
   нажмите «Создать ключ».
2. Программа сгенерирует 32 случайных байта и покажет ключ строкой.
   На шлюз уходит только `sha256(ключ)`, сам ключ остаётся на вашем компьютере.
3. В карточке пользователя нажмите «Настроить» и задайте его сайты, квоты
   и скорость. Эти ограничения действуют только на него.
4. Нажмите «Пригласить» — скачается файл `Иван.exitnode` с адресом шлюза
   и ключом. Передайте его коллеге любым личным каналом.
5. Коллега открывает файл в клиенте (см. ниже) — и всё, вводить ничего не нужно.
6. «Отозвать» удаляет ключ из панели и со шлюза; следующее подключение
   с этим ключом будет отклонено.

Ключ равносилен паролю: кто его получил, тот пользуется вашим выходом.
Смена ключа = создание нового и отзыв старого.

## Клиент — программа коллеги

Браузеры не умеют передавать логин и пароль в SOCKS5, поэтому коллега запускает
небольшой локальный клиент, который сам подставляет ключ.

### Окно клиента

```
proxy.exe client
```

Открывается окно: адрес шлюза, ключ, кнопка «Подключить», локальный прокси
`127.0.0.1:1080`, счётчики трафика и подсказка для браузера. Настройки
сохраняются в `%LOCALAPPDATA%\exitnode\client.json`, при следующем запуске
клиент подключается сам.

Приглашение от владельца узла:

```
proxy.exe client -invite "Иван.exitnode"
```

Файл содержит адрес шлюза и ключ; клиент импортирует его, подключится и
откроет окно. То же самое можно сделать кнопкой «Открыть файл приглашения».

### Консольный режим

Для скриптов и Linux остаётся прежний вариант:

```
proxy.exe client -server 10.8.0.1:1080 -key-file key.txt -tls -server-name proxy.example.com
```

- `-tls` обязателен вне локальной сети: ключ передаётся только внутри TLS 1.3.
- `-server-name` нужен, если в адресе указан IP, а сертификат выписан на домен.
- `-key-file` читает ключ из файла, чтобы он не светился в списке процессов.
- `-insecure` отключает проверку сертификата — только для теста.

В обоих режимах клиент поднимает SOCKS5 на `127.0.0.1:1080` без пароля.
Если порт 1080 занят (например, Xray или другой прокси), клиент автоматически
берёт следующий свободный в диапазоне 1081–1099 и показывает его в окне.
Указывайте в браузере именно этот порт.

Проверка из терминала:

```
curl --socks5-hostname 127.0.0.1:1080 https://ifconfig.me/
```

Команда должна показать IP коллеги, а не ваш.

Для Chrome/Edge отдельный ярлык:

```
chrome.exe --proxy-server="socks5://127.0.0.1:1080" ^
  --force-webrtc-ip-handling-policy=disable_non_proxied_udp
```

Флаг WebRTC обязателен: без него браузер отдаёт реальный IP через STUN в обход
прокси. Это главная причина утечек, а не сам прокси.

## Ограничения пользователей

На вкладке «Пользователи» у каждого ключа своя карточка. «Настроить» открывает:

- **Разрешённые сайты** — белый список именно для этого человека.
  `example.com` разрешает и все поддомены. Пусто — любые сайты.
- **Квота в сутки** — при достижении его активные подключения обрываются,
  новые отклоняются до следующего дня. `0` — без лимита.
- **Квота в месяц** — то же самое, счётчик сбрасывается первого числа.
- **Скорость** — потолок только для его подключений, КБ/с. `0` — без лимита.

Там же видно, сколько он израсходовал за день и за месяц и сколько у него
активных подключений. Изменения действуют сразу, без перезапуска.

Состояние хранится в `%LOCALAPPDATA%\exitnode\agent-state.json` и переживает
перезапуск. Счётчики сбрасываются в полночь и первого числа по местному времени.
Флаги `-quota-mb`, `-quota-month-mb`, `-rate-kbps`, `-allow-domains` задают
значения по умолчанию для новых ключей.

## Защита

- Агент блокирует `127.0.0.0/8`, `10/8`, `172.16/12`, `192.168/16`,
  `169.254/16`, `100.64/10` и прочие служебные диапазоны. Клиент не попадёт
  в роутер или принтер коллеги.
- Домен резолвит агент и подключается уже к проверенному IP — это исключает
  DNS-rebinding.
- По умолчанию разрешены только порты 80 и 443.
- Клиент без действующего ключа не проходит авторизацию на шлюзе; отозванный
  ключ перестаёт работать сразу, повторная отправка списка ключей идёт по таймеру.
- Соединение клиента со шлюзом шифруется TLS 1.3: ключ не идёт открытым текстом.
- Сквозное шифрование: клиент отправляет шлюзу только `sha256` ключа и фиктивный
  адрес, настоящая цель и трафик идут внутри AES-256-GCM. Шлюз не видит ни ключ,
  ни сайты, ни содержимое.
- Панель проверяет `Host` и `RemoteAddr`, поэтому DNS-rebinding на `127.0.0.1`
  не проходит; ключи в общем списке замаскированы и выдаются по отдельному запросу.
- Без `-cert/-key` шлюз запускается только с `-dev`, случайно открытый
  незашифрованный туннель поднять нельзя.
- Шлюз ограничивает число одновременных SOCKS- и туннельных соединений,
  у агента лимит считается с учётом ещё не установленных сессий.
- Управляющие запросы панели требуют кастомный заголовок, поэтому сторонний
  сайт не сможет выключить узел через CSRF.
- Панель слушает только `127.0.0.1`.

## Чего пока нет

- UDP (звонки, игры) — только TCP.
- IPv6-адреса целей.
- Установщика и автообновлений.
- Оплаты, квот и учёта трафика по отдельным клиентам.
