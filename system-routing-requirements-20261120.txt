ЦЕЛЬ ПОЛЬЗОВАТЕЛЯ

После включения клиент явно видит, какой сайт/сервис направлен через какой узел владельца. Правило должно работать в браузере и в других приложениях, включая не использующие системные HTTP/SOCKS-настройки.
Согласие с выводами security-review-20261120.txt учтено. Исправления безопасности остаются обязательным этапом перед выпуском системного режима.

ЦЕЛЕВОЙ ИНТЕРФЕЙС

Карточка маршрута показывает:
- сайт/сервис и точный набор доменов, включая API/CDN, если они нужны;
- имя узла, его закреплённый идентификатор и понятную подпись владельца;
- режим: только выбранные назначения или всё выбранное приложение;
- готовность системного перехвата и аутентифицированного канала к агенту;
- разрешения владельца: порты, квота/остаток, скорость, срок доступа;
- свежесть проверки и конкретную причину блокировки.

Имена узла и владельца — подписи, а не доказательство личности человека. Узел подтверждается закреплённым ключом; проверка человека зависит от канала выдачи приглашения.

Пример, не фактические данные:
example.com -> узел «Anna-Tallinn» -> системный маршрут активен.
Текущие соединения через этот маршрут: 2; остаток квоты: 1,2 ГБ.

Статусы:
- Выключено: системный режим явно выключен пользователем.
- Подготовка: установка маршрутов/фильтров и проверка узла.
- Правило активно: перехват готов и узел аутентифицирован; это готовность, не утверждение о наличии трафика.
- Трафик через узел: есть соединения, действительно направленные и открытые через агент.
- Заблокировано: квота, отзыв, недоступность узла или неподдерживаемый трафик.
- Требуется настройка: назначение приложения нельзя надёжно определить.

Запуск локального слушателя не означает «защищено». Проверка служебного канала не доказывает доступность каждого сайта. Полезно отдельно показывать успешное открытие выбранной цели через агент, не выдавая его за доказательство всех будущих соединений.

АРХИТЕКТУРА

Приложение пользователя -> системный сетевой слой -> правила маршрутизации ->
аутентифицированный канал -> relay -> agent -> разрешённая цель.
Остальной трафик следует явно выбранной политике, без использования агента владельца.

Общая логика клиента: правила, DNS-сопоставление, шифрованный канал, состояние и счётчики.
Платформенные модули: установка виртуального интерфейса, маршруты, DNS, firewall, запуск службы и восстановление настроек.

Windows 11:
- TUN-адаптер, например официальный подписанный Wintun, и пользовательский TCP/IP-стек.
- Сетевой helper/service с необходимыми правами.
- WFP/системная фильтрация для исключения обхода и защиты при сбое.
- GUI работает без повышенных прав; управление службой через IPC с ACL.
- Установка системного компонента потребует повышения прав.

Linux:
- /dev/net/tun, маршрутизация IPv4/IPv6 и интеграция с DNS конкретной системы.
- Служба с ограниченными привилегиями, включая необходимые сетевые capabilities.
- Правила nftables либо совместимый системный механизм для запрета обхода.
- GUI/CLI без постоянного запуска от root; аутентифицированный локальный IPC.
- Дистрибутивы и менеджеры сети для первой поддерживаемой сборки ещё не определены.

TUN обеспечивает получение IP-пакетов; сам по себе он не распознаёт домены, не преобразует пакеты в текущий TCP-протокол и не предотвращает обход при аварии. Нужны стек, DNS-логика и независимая фильтрация.
Для Windows возможен альтернативный путь WFP connect-redirection, но он требует callout-драйвера и более сложного распространения. Для двух платформ предпочтительно общее TUN-ядро с адаптерами ОС; окончательный выбор библиотеки требует проверки лицензии и совместимости.

ПОЛИТИКА ВЛАДЕЛЬЦА

После надёжной аутентификации клиент получает от агента версию разрешений и актуальные условия. Ключ/ID узла закрепляется приглашением; одного поля name недостаточно.
Клиент может выбрать только подмножество разрешений владельца. Агент проверяет каждое соединение независимо от клиента/relay. Изменение правил требует пересмотра и закрытия затронутых активных/ожидающих соединений.
Приглашение — средство первичного подключения; его копия условий не заменяет актуальную политику агента.

ДОМЕНЫ И DNS

Для приложений, использующих контролируемый DNS, предпочтительно сопоставление через fake-IP: приложению выдаётся виртуальный адрес, клиент сохраняет соответствие домену, TUN восстанавливает домен, реальный DNS и Dial выполняет агент.
Это уменьшает неоднозначность общих CDN-IP. Нужны A/AAAA, TTL, сохранение/очистка сопоставлений и управление старым DNS-кешем.
Список доменов сервиса может включать основной сайт, API, авторизацию, загрузки и CDN. Дополнительные домены не должны автоматически расширять согласие владельца.

ГРАНИЦЫ ГАРАНТИЙ

Системный перехват охватывает программы, игнорирующие proxy-настройки, но не делает имя назначения всегда видимым. Приложения могут иметь собственный DoH/DoT, кеш, соединение по IP; ECH скрывает имя в TLS. HTTP/2 может объединять несколько имён в одном соединении.
Если неизвестные соединения свободно выпускать напрямую, нельзя одновременно гарантировать, что скрытое назначение выбранного сервиса не уйдёт напрямую.

Для таких программ необходим один из вариантов:
1. Поддерживаемый профиль приложения с управляемым DNS и проверкой совместимости.
2. Режим всего приложения через узел: допустимое разрешениями владельца проксируется, остальное блокируется. Это не означает, что любая программа будет полностью работоспособна при узком allowlist.
3. Строгая блокировка неопознанных соединений в согласованной области защиты.

Не обещать «любое приложение и только один сайт без исключений». Без расшифровки HTTPS нельзя строго определить содержимое всех ресурсов на общем сервере. Внедрение собственного корневого сертификата и MITM не входит в это решение.

ОБРЫВЫ, ОСТАНОВКА И ЗАПУСК

При активной защите недоступность relay/агента, ошибка аутентификации, отзыв ключа и исчерпание квоты не должны включать DIRECT для защищённого трафика.
Фильтры защиты должны действовать при падении GUI/сетевого процесса; исчезновение TUN или маршрутов не должно молча открывать прямой путь. Исключения для самого туннеля и необходимых сетевых служб должны быть ограничены.
Прямое соединение к выбранному сервису, открытое до включения, нельзя перенести внутрь прокси: нужно завершить и установить его заново. До подтверждения отсутствия старых обходящих соединений не показывать полную готовность.
Явное выключение пользователем и авария — разные состояния. Выход из GUI не должен снимать защиту, если режим ещё активен. Возврат к обычной сети делается отдельным понятным действием. Удаление восстанавливает настройки по согласованной политике, не уничтожая чужие firewall/маршруты.
Локальный администратор/root может отключить службу и фильтры; защита не рассчитана на противодействие полному контролю ОС её владельцем.

TCP И UDP

Текущий протокол передаёт TCP. Для полноценной поддержки приложений с UDP потребуется расширение транспорта client/relay/agent, ограничения направлений и объёма UDP и отдельная проверка безопасности.
До реализации UDP выбранный неподдерживаемый UDP должен блокироваться, а интерфейс — сообщать ограничение. Некоторые приложения перейдут с QUIC на TCP, другие не заработают; универсальную совместимость обещать нельзя.

ПРОВЕРЯЕМЫЕ ЭТАПЫ

1. Исправить ошибки безопасности: обязательная аутентификация перед агентом и защита replay, отзыв/выключение, таймауты, учёт скорости.
2. Добавить подтверждённую политику узла и достоверные статусы клиента.
3. Реализовать общий сетевой движок и DNS-правила, отдельно адаптеры Windows/Linux.
4. Реализовать независимую защиту от прямого выхода, жизненный цикл и безопасное восстановление сети.
5. Проверить на Windows 11 и выбранных Linux-дистрибутивах: браузер, программа без proxy-настроек, IPv4/IPv6, DNS-кеш, обрыв, падение процесса, смена сети, отзыв и квота.
6. Отдельно внедрить и проверить UDP либо явно ограничить выпуск TCP-приложениями.

Критерий проверки: контролируемый тестовый сервер назначения подтверждает выход через сеть владельца; локальная проверка соединений/пакетов подтверждает отсутствие прямого выхода защищённого назначения; UI показывает ровно проверенное состояние. Публичный сторонний сервис проверки IP не требуется для каждого старта и не должен получать необязательные запросы без объяснения.
Конкретные приложения и сайты для приёмки пользователь пока не назвал.
