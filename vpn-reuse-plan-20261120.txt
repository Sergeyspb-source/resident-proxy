ВЫВОД

Можно использовать сетевые механизмы VPN в отдельном приложении прокси. Наиболее прямой первый путь — адаптировать уже использованный в VPN движок sing-box для клиентского TUN, доменных правил и отправки выбранных соединений в существующий локальный SOCKS exitnode. Это сохраняет независимость от VPN V2 и не требует писать преобразование IP-пакетов в TCP-соединения самостоятельно.
Это техническая рекомендация по исходникам и отчётам, а не подтверждение готовности отдельной сборки.

ПРЕДЛАГАЕМАЯ СХЕМА ОТДЕЛЬНОГО КЛИЕНТА

Браузер/программа -> клиентский TUN + правила -> локальный SOCKS exitnode ->
защищённый client/relay/agent -> разрешённый сайт с выхода владельца.

Для прочих назначений движок использует явно выбранный обычный маршрут ОС. При уже включённом VPN этот обычный маршрут может проходить через VPN; надпись «direct» не равнозначна «мимо любого VPN». Интерфейс должен объяснять это без ложных обещаний.
Локальный SOCKS-порт берётся из состояния exitnode, а не жёстко задаётся 1080: текущий клиент выбирает свободный порт.
Нельзя направлять sing-box прямо на relay как на обычный SOCKS-сервер: exitnode использует собственный обмен хешем и E2E. Локальный client должен сохранять роль адаптера этого протокола.

ЧТО НУЖНО АДАПТИРОВАТЬ

- Серверный RenderTUN использует auto_route:false, strict_route:false и интерфейс egress0 для forwarded VPN пакетов. Эти настройки нельзя без изменений ставить на ПК клиента.
- Нужны клиентские DNS-правила и точное сопоставление доменов, исключение самого relay/служебных соединений из перехвата, защита от циклов.
- Нужны управление привилегированным процессом, конфигурация без секретов в логах/аргументах, установка и корректное восстановление сети для Windows/Linux.
- Для строгого режима нужны независимые фильтры, сохраняющие блокировку при аварии движка. TUN и правило «без direct fallback» сами по себе не закрывают исчезновение маршрутов при смерти процесса.
- Условия, квоты и имя/ID узла клиент должен получать по аутентифицированному каналу от агента; в exitnode этого обмена пока нет.
- Текущие ошибки exitnode из security-review-20261120.txt должны быть исправлены независимо от выбора сетевого движка.
- SOCKS exitnode поддерживает TCP CONNECT. Поддержка UDP самим sing-box не добавляет её в наш relay/agent: до расширения транспорта выбранный UDP блокировать с понятным статусом.

АЛЬТЕРНАТИВА: ПЕРЕНОС СВОИХ GO-ПАКЕТОВ

Можно выделить Wintun/WFP Windows и TUN/network Linux в независимый сетевой модуль. Это даёт больше контроля, но не заменяет TCP/IP-стек для преобразования пакетов в потоки текущего прокси.
VPN pump пересылает IP-пакеты через V2 SendData (client-linux/internal/session/pump.go:75–86). Exitnode переносит TCP-потоки; форматы напрямую несовместимы. Переносить ради этого весь V2, каскады и управление VPN не требуется.
Пакеты internal нельзя импортировать из exitnode напрямую по правилам Go; нужны отдельный доступный модуль либо контролируемое извлечение с тестами.

ГРАНИЦЫ ПОДТВЕРЖДЕНИЯ

- docs/gates/kill-switch-1.md: Windows защита проверена при обрыве сессии; смерть процесса и reboot phase 2 не покрыты. Динамические WFP-фильтры исчезают с процессом.
- Linux TUN/маршруты/DNS имеют документированные проверки, но не доказывают работу селективного прокси-клиента.
- Доменное разделение произвольных программ всё ещё требует учёта DoH/ECH, DNS-кеша и общего CDN-IP; наличие VPN не снимает эти ограничения.
- Нельзя обещать бесконфликтную одновременную работу с текущим VPN без отдельной проверки.

У отдельного приложения должны быть свои имена адаптера, службы, файлы настроек, каталоги и локальные порты; на Linux — собственные идентификаторы таблиц/правил. Изменять и удалять только собственные сетевые объекты. Нельзя копировать VPN адреса 10.77.0.x, имена vpn0/vpn-test и таблицу 4242 как готовые продуктовые значения.
Готовность проверять сначала в изолированной среде; работающий VPN не использовать как полигон без отдельного согласованного прогона.
