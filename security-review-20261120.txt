ОЦЕНКА

Архитектура подходит для управляемого выхода в интернет через компьютер добровольного владельца. Уже есть индивидуальные ключи, квоты, домены и защита локальной сети. Для широкого распространения сначала нужно устранить ошибки авторизации и прекращения доступа. Прохождение тестов не подтверждает безопасность всей системы.

Термины:
- Владелец узла: человек, предоставляющий свой канал и внешний IP; у него agent.
- Клиент: человек, использующий этот выход; у него client.
- relay: шлюз на VPS2, связывающий клиента с нужным агентом.
- hop: необязательный TCP-переадресатор на VPS1.

КАК УСТАНАВЛИВАЕТСЯ СОЕДИНЕНИЕ

1. Агент подключается исходящим TCP к relay. Открывать входящий порт на домашнем роутере не нужно, NAT/CGNAT обычно не мешают. По умолчанию используется TLS 1.3 с проверкой сертификата шлюза, затем общий токен агентов и yamux для нескольких потоков. Это НЕ mTLS: клиентские сертификаты агента в конфигурации TLS не запрашиваются.
2. Владелец создаёт отдельный случайный ключ доступа для каждого клиента и задаёт условия. Агент сообщает шлюзу ID, подпись и SHA-256 ключа. Полный ключ остаётся у владельца и получателя приглашения.
3. Файл приглашения клиента содержит server/key/name/version. В действующем формате нет срока действия, привязки к устройству, списка сайтов, квоты или отдельного TLS server_name.
4. Клиент импортирует приглашение и запускает локальные SOCKS5 и HTTP-прокси. В графическом режиме соединение со шлюзом использует TLS. Кнопка «Подключить» фактически запускает локальные слушатели; реальное соединение со шлюзом создаётся при запросе сайта, поэтому статус Running не доказывает доступность агента и корректность ключа.
5. Браузер должен использовать этот прокси: через системную настройку Windows, настройку самого браузера или отдельный профиль. Сам импорт приглашения не перехватывает весь трафик компьютера.
6. Например, для https://example.com браузер делает CONNECT example.com:443 к локальному HTTP-прокси либо SOCKS5 CONNECT. Клиент соединяется со шлюзом напрямую или через hop, передаёт SHA-256 ключа как SOCKS-пароль и фиктивную цель e2e.invalid:443.
7. Шлюз по хешу находит нужный подключённый агент. Конкретный узел выбирается ключом, а не сайтом; пула с автоматическим подбором страны/узла здесь нет.
8. Клиент внутри AES-GCM потока передаёт настоящие example.com и 443. Агент проверяет ключ, квоту, разрешённый домен и порт, разрешает DNS сам, проверяет все адреса и открывает TCP к проверенному IP.
9. Браузер устанавливает HTTPS с сайтом через этот канал. Сайт видит внешний адрес сети владельца узла, который может быть общим адресом провайдера при CGNAT.

Маршрут: браузер -> локальный client -> [VPS1 hop] -> VPS2 relay -> agent владельца -> сайт.

В нормальном E2E-режиме relay не получает настоящий домен и содержимое, но видит хеш ключа, идентификаторы, IP соединений, время и объём. При использовании hop relay видит адрес hop, без hop — адрес клиента. Владелец агента видит домены; обычный HTTP виден открытым текстом. Содержимое HTTPS остаётся защищённым HTTPS при нормальной проверке сертификата браузером.

ТОЛЬКО КОНКРЕТНЫЕ САЙТЫ ЧЕРЕЗ УЗЕЛ

Текущий allowlist — запрет нежелательных назначений НА АГЕНТЕ. Он не является настройкой выбора маршрута на клиенте. Если весь браузер отправлен в прокси, неразрешённый сайт получит отказ; автоматического прямого маршрута для остальных сайтов нет.

Для режима «example.com через узел, остальные напрямую» нужна отдельная клиентская настройка: PAC либо расширение/правила прокси. Для выбранных доменов нельзя добавлять незаметный DIRECT fallback при ошибке, если требуется скрывать IP клиента. Нужно отдельно учитывать ресурсы сайта на CDN и других доменах.

Это TCP-прокси, не VPN всего устройства. UDP, QUIC, WebRTC и приложения, игнорирующие системный прокси, требуют отдельного решения и проверки на утечки. При передаче IP вместо доменного имени allowlist доменов не сможет сопоставить его с сайтом; SOCKS должен передавать имя для remote DNS.

ПЛЮСЫ, ПОДТВЕРЖДЁННЫЕ КОДОМ

- Владелец сам создаёт ключи; при чистом состоянии без ключей клиентский доступ отсутствует.
- Ключи генерируются crypto/rand, 32 байта; ID не является частью ключа.
- Индивидуальные суточные и месячные квоты; учитываются полезные байты в обе стороны. Достижение квоты вызывает закрытие зарегистрированных сессий ключа.
- Отдельные ограничения доменов и скорости; стандартные разрешённые порты 80/443.
- DNS на агенте; соединение по уже проверенному IP. Блокируются private, loopback, link-local, CGNAT и ряд опасных IPv6 диапазонов.
- Панели ограничены loopback, проверяются Host и RemoteAddr; изменяющие запросы требуют специального заголовка, есть ограничения тела/заголовков и таймауты.
- TLS 1.3, ограничение служебных строк, лимиты потоков/подключений и размера кадров.
- Предусмотрены файлы nftables и fail2ban. Их наличие в репозитории не доказывает установку на сервере.
- Подписанный Ed25519 манифест релизов. Сейчас проверка сообщает статус манифеста, но не является обязательной проверкой скачанного/запущенного бинарника.

ПРИОРИТЕТНЫЕ ПРОБЛЕМЫ

P1. НЕОБЯЗАТЕЛЬНОЕ E2E ПОЗВОЛЯЕТ ОБОЙТИ ПРОВЕРКУ ЗНАНИЯ ПОЛНОГО КЛЮЧА
Места: internal/relay/socks.go:87,120; internal/agent/agent.go:343,369,377,393.
Шлюз принимает хеш как bearer credential. Агент выбирает E2E только при host == e2e.invalid; остальные запросы выполняет без криптографического подтверждения знания полного ключа. Поэтому утечка хеша при наличии сетевого доступа к SOCKS позволяет использовать обычную ветку, а захват relay позволяет инициировать её напрямую по известному KeyID. Квоты и Guard продолжают действовать, но отдельное согласие владельца на такого пользователя отсутствует.
Минимальная мера: запретить обычную ветку на агенте и требовать E2E. Это ограничит совместимость со старыми клиентами; сам по себе такой запрет ещё не решает replay.
SECURITY.md слишком мягко описывает последствия pass-the-hash. README ошибочно подписывает TLS-канал как mTLS.

P1. ОТЗЫВ КЛЮЧА И ВЫКЛЮЧЕНИЕ НЕ ОСТАНАВЛИВАЮТ ВСЮ РАБОТУ
Места: internal/agent/agent.go:570,656,798; internal/ui/index.html:776.
SetEnabled меняет только флаг для новых запросов. RemoveKey удаляет ключ, но не вызывает KillByKey. Старые соединения продолжаются; addTraffic при отсутствии ключа просто возвращается, поэтому после отзыва их квота больше не учитывается. Изменение allowlist тоже не пересматривает уже открытые соединения. При новом запуске Run всегда включает агент (agent.go:154), прежнее выключенное состояние не сохранено.
Минимальная мера: атомарное запрещение новых соединений и закрытие активных/ожидающих при отзыве или выключении; повторная проверка ключа и enabled при регистрации после Dial. Просто добавить KillByKey без защиты гонки недостаточно. Сохранять состояние выключения.

P1. САМОПИСНЫЙ E2E НЕ ПРИВЯЗЫВАЕТ КАДРЫ К СЕССИИ И НАПРАВЛЕНИЮ
Места: internal/secure/secure.go:19,57,61,96.
Для ключа доступа используется один производный ключ AES-GCM во всех соединениях и направлениях. Нет обмена свежими параметрами сессии, порядковых номеров или проверки повторов. Случайный nonce обеспечивает уникальность новых кадров с высокой вероятностью, но не запрещает повторное предъявление уже записанного кадра. Скомпрометированный relay способен повторить записанный E2E-запрос и последующие кадры. Последствия для HTTP/других протоколов зависят от содержания; внутренний HTTPS имеет собственную защиту и не означает автоматически успешный повтор действий на сайте. При последующей утечке полного ключа доступна расшифровка сохранённых внутренних кадров: собственной forward secrecy здесь нет.
Мера: стандартный аутентифицированный защищённый канал между клиентом и агентом с проверенной библиотекой, свежими ключами сессии и защитой от повтора. Не считать добавление ещё одного статического хеша решением.

P2. НЕЗАВЕРШЁННОЕ E2E МОЖЕТ ЗАНЯТЬ ВСЕ СЛОТЫ
Места: internal/agent/agent.go:320,443,452,456,487.
Агент снимает read deadline перед чтением внутреннего E2EConnect. Созданный context не прерывает чтение сокета. Молчащий поток занимает MaxSessions, но ещё не зарегистрирован в Registry, поэтому кнопка KillAll его не видит. Для атаки нужен доступ через хеш/шлюз.
Мера: deadline до окончания аутентификации и запроса цели; отдельный учёт и отмена ожидающих потоков, ограничения на ключ.

P2. ЛИМИТ СКОРОСТИ РАБОТАЕТ ТОЛЬКО НА СКАЧИВАНИЕ КЛИЕНТОМ
Места: internal/agent/agent.go:531,538,546.
Read не вызывает limiter. Upload клиента через узел не ограничивается скоростью, хотя учитывается в квоте. Ошибка WaitN игнорируется.
Мера: явно определить общий/раздельный лимит направлений и применять его к обоим; обрабатывать отмену ожидания.

P2. КЛЮЧИ И УПРАВЛЕНИЕ ДОСТУПНЫ ЛОКАЛЬНЫМ ПРОЦЕССАМ
Места: internal/limits/limits.go:21,126; internal/clientui/app.go:65; internal/ui/server.go:158,334,390.
Ключи и токен сохраняются открытыми. Локальный API не требует секрета сессии: любой подходящий локальный процесс может раскрыть ключ или получить приглашение узла с общим токеном. Host и X-Requested-With защищают от ряда браузерных атак, но не аутентифицируют локальный процесс.
Мера: индивидуальные credentials узлов вместо общего токена, токен сессии локальной панели, явные Windows ACL, защита сохранённых секретов DPAPI/Credential Manager. DPAPI уменьшает риск копирования файлов и доступа других учётных записей, но не защищает от вредоносного процесса того же пользователя.

ОГРАНИЧЕНИЯ СПИСКА САЙТОВ

internal/agent/guard.go:56,83 проверяет имя назначения, а затем передаёт произвольные TCP-байты. Он не проверяет URL-пути, категории контента, HTTP Host или TLS SNI. На общем IP/CDN возможность обратиться к другому виртуальному хосту зависит от поведения сервера. Разрешённый сайт сам может предоставлять туннелирование. Формулировка «только эти TCP-назначения» точнее абсолютной гарантии «никакие другие сайты».
example.com включает все поддомены. Пустой список разрешает всё. DomainList также может нормализовать ввод из одних разделителей/точек в пустой список; нужна валидация и явный режим «запретить всё».

УСЛОВИЯ ДЛЯ ВЛАДЕЛЬЦА

Сейчас новый ключ сразу активен с defaultLimits; по стандартным флагам это все домены и отсутствие квот/скорости. Общей квоты компьютера нет: несколько клиентов расходуют сумму индивидуальных квот. Срок действия и привязка ключа к устройству отсутствуют; файл приглашения можно скопировать.
Установщик агента включает автозапуск и запускает его в трее; нужно отдельное понятное согласие. При чистом состоянии это ещё не даёт трафик без выдачи ключа.

Рекомендуемая карточка согласия ДО активации ключа:
- кому предоставляется выход и с какого устройства;
- разрешённые домены, отдельно политика поддоменов;
- квота клиента на день/месяц и общая квота владельца;
- скорость обоих направлений и число соединений;
- срок действия, часы работы и автозапуск;
- сайт видит внешний IP сети владельца, что может привести к CAPTCHA, жалобам и блокировкам этого адреса;
- кнопка «Остановить доступ сейчас», немедленно закрывающая все соединения.

Квота считает TCP payload в обоих направлениях, а не счётчик провайдера: служебные данные TLS/yamux/E2E и повторные передачи в неё не входят. Порог проверяется после порции данных, поэтому возможен небольшой перерасход на параллельных потоках. Состояние записывается раз в 5 секунд и при достижении квоты; авария может потерять последние данные. В flushLimits снимок делается до saveMu: порядок записи двух снимков потенциально может оказаться обратным (agent.go:880). Для жёсткой тарификации нужны более строгие гарантии сохранения.

ПОРЯДОК ДОРАБОТОК

1. Немедленная остановка при отзыве/выключении, учёт ожидающих соединений и защита гонок; deadline E2E.
2. Запрет нешифрованной ветки; затем стандартная аутентификация клиента перед агентом и защита от replay.
3. Безопасные настройки до активации, срок действия, индивидуальные credentials узлов, локальная защита секретов.
4. Лимит скорости в обе стороны и общая квота владельца.
5. Клиентская маршрутизация по доменам и проверка утечек в реальном браузере.
6. Проверка реального развёртывания: TLS, отсутствие insecure/plain/dev, firewall, права файлов, отдельный непривилегированный пользователь сервиса, наличие работающих fail2ban/nftables. В этом обзоре сервер не проверялся.
